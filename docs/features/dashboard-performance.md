# Dashboard 首屏性能优化

## 1. 要解决什么问题

Dashboard 下所有页面（`/knowledge`、`/users`、`/audit-logs` 等）首屏**整页白屏超过 10s**，且**每次刷新都慢**。

根因有两层，叠加导致体感极差：
1. **无路由骨架**：`(dashboard)` 路由组没有任何 `loading.tsx`，路由切换/刷新时 Next.js 连骨架都不渲染，纯客户端组件在 JS 加载执行前是一片白屏。
2. **数据请求实时穿透**：只读列表类接口每次都实时穿透到外部服务（如 SenseCore 云端），外网延迟/抖动直接传导到首屏，刷新一次慢一次。

**目标**：页面骨架即时渲染（不白屏），数据异步填充；只读且数据变动不频繁的接口通过短 TTL 缓存让刷新接近秒开。

## 2. 需求清单

- [x] R1 · 消除路由白屏：给 `(dashboard)` 路由组加全局 `loading.tsx`，路由切换/刷新时立即渲染骨架屏
- [x] R2 · BFF 短 TTL 缓存能力：在 NestJS 层提供通用内存缓存（可配置 TTL，默认 30s~5min）
- [x] R3 · 缓存按租户隔离：缓存 key 必须含 `facility_id`，杜绝跨租户读到他人缓存（红线）
- [x] R4 · 只读非 PHI 接口接入缓存：knowledge datasets 列表等只读外部接口接入 R2，刷新命中缓存接近秒开
- [x] R5 · 超时兜底：收紧外网调用超时（120s→约 15s），超时返回降级结果而非无限拖住页面
- [x] R6 · 手动刷新绕过缓存：页面提供刷新入口时可强制实时拉取

## 3. 接口设计（分层标注）

| 层 | 改动 | 说明 |
|---|---|---|
| **web** | 新增 `(dashboard)/loading.tsx` | 纯展示骨架，复用现有 `Skeleton` 组件，消除白屏 |
| **api (BFF)** | 新增 `cache/` 模块（全局） | `CacheService`（进程内内存缓存 + TTL 抖动）+ `@Cacheable()` 装饰器 + `CacheInterceptor`（全局 APP_INTERCEPTOR），key 含 `facility_id` |
| **api (BFF)** | knowledge 只读 GET 接入缓存 | `GET /knowledge/datasets` 标 `@Cacheable(60s)`；写操作（建/删数据集、上传文档）后按 `facility_id` 前缀失效缓存 |
| **inference** | 收紧外网调用超时 | httpx 超时 120s→连接 10s/读 15s + 连接池限制，超时走既有降级分支 |

> 不新增业务接口，不改任何对外 API 签名。缓存复用 `@Audit` 同款「装饰器存元数据 + 全局拦截器执行」模式。

## 4. 数据模型

无 entity 变更，不涉及 `packages/db`。缓存为 BFF 进程内内存缓存，不落库。

## 5. 边界 Case（重点）

**缓存正确性**
- 跨租户越权：两个不同 `facility_id` 的用户请求同一接口，必须各自命中各自的缓存。→ key 强制以 `facility_id` 开头；写操作失效也按 `facility_id` 前缀，天然租户隔离
- 缓存雪崩：大量 key 同时过期导致瞬时回源风暴。→ TTL 加 ±10% 随机抖动，60s 定时清理过期 key
- 数据不一致：缓存窗口内数据被修改，用户刷新看到旧数据。→ 接受分钟级延迟（已与需求方确认）；写操作后主动失效 + 手动刷新走 `x-cache-bust` 绕过
- 进程重启：内存缓存丢失。→ 可接受，重启后回源重建

**并发与超时**
- 重复调用：同一租户高频刷新，缓存未命中时是否回源打爆下游。→ 单飞（single-flight）：同一 key 并发请求只回源一次，其余等待共享结果
- 超时传导：外网慢调用无限拖住首屏。→ inference 超时兜底走降级分支，页面先渲染
- **下游服务卡死**（实现中实测发现）：FastAPI 进程卡死/端口被孤儿套接字占用时，BFF 转发要等 `FORWARD_TIMEOUT_MS`（默认 30s）才报 503，页面长时间转圈。→ 已知限制：`/health` 都无法响应说明问题在进程层而非业务层，需重启恢复；如需更快失败可调小 BFF 转发超时（待决策）

**PHI 红线**
- 缓存内容必须为非 PHI：只缓存 knowledge datasets、列表类等明确不含患者数据的只读接口；涉及病历/患者的接口一律不缓存
- 无租户上下文（无法解析 `facility_id`）时不缓存，降级为直接透传，避免跨租户污染
- 日志/报错不得输出缓存内容中的敏感信息

**审计**
- 列表类只读接口已有 `@Audit` 注解，缓存命中不改变审计行为（仍记录访问）

## 6. 依赖与被调用

- **上游**：dashboard 各页面（消费方，无需改动，loading.tsx 自动生效）
- **下游**：inference 的 knowledge 路由、SenseCore 云端（被缓存，减少回源）
- **被谁影响**：BFF 租户上下文（缓存 key 依赖 `getFacilityId()` 注入）；`x-cache-bust` 请求头由前端手动刷新触发

## 7. 验收标准

- [ ] 刷新任一 dashboard 页面，骨架屏在 200ms 内出现，无整页白屏（**待浏览器实测**）
- [ ] knowledge 页面二次刷新（缓存窗口内）数据区在 1s 内填充（**待浏览器实测**）
- [x] 两个不同租户同时请求，各自只看到自己的数据（无串租户）—— key 含 facility_id，单测通过
- [ ] 外网接口超时（模拟 15s+）时页面不卡死，显示降级提示（**待实测**；inference 超时已收紧至 15s 走降级分支）
- [x] 同一租户高频刷新，下游回源请求数不随刷新次数线性增长（单飞生效）—— 拦截器单飞逻辑已实现

## 8. Out of Scope

- 不做 SSR/服务端数据预取改造（保持客户端组件，仅加骨架）
- 不做 Redis 等分布式缓存（单实例内存缓存即可，后续多实例再升级）
- 不缓存 PHI 相关接口、不缓存写操作
- 不优化 SSE 流式问答接口（chat/stream）
- 不动 `packages/db`、不新增 npm 依赖（缓存用 NestJS 内置或原生实现）
- 不处理「下游进程卡死时 BFF 快速失败」（见第 5 节已知限制，需单独决策是否调小 `FORWARD_TIMEOUT_MS`）
